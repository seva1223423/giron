## Git

**Правило:** После каждого `git commit` сразу делать `git push origin master`.
**Why:** Пользователь смотрит на GitHub и видит устаревшие данные. Локальные коммиты без пуша воспринимаются как отсутствие работы. Однажды 5 коммитов пролежали локально несколько часов — пользователь заметил и был недоволен.
**How to apply:** Всегда `git commit -m "..." && git push origin master` в одной команде.

## Memory

**Правило:** После значимых изменений обновлять оба места:
1. `C:/Users/sevka/.claude/projects/C--Users-sevka-Desktop-1223/memory/` (глобальная memory)
2. `<repo>/memory/` (memory в репозитории — резервная копия)

**Why:** Пользователь однажды вышел из VS Code и потерял memory — она была привязана к другой рабочей директории. Дублирование в репозитории гарантирует сохранность.

**Путь в репо — `memory/`, НЕ `.claude/memory/`.** Всё что внутри `<repo>/.claude/` Claude Code считает sensitive и принудительно спрашивает разрешение на каждое изменение — этот guard не отключается через settings. Memory переехала из `.claude/memory/` в `memory/` именно поэтому. НЕ класть туда обратно.

**How to apply:** Обновлять оба места синхронно. MEMORY.md — это индекс, не содержит сам контент.

## Стиль ответов

**Правило:** Краткие ответы. Не резюмировать что только что сделал.
**Why:** "Я и так вижу diff / результат команды."
**How to apply:** Сказал — сделал. Итог одной фразой максимум.

## Автономность

**Правило:** Пользователь говорит "делай сам / продолжай / дальше / максимально" → выполнять автономно, без промежуточных согласований.
**Why:** Доверяет архитектурным решениям если они разумны. Не любит объяснения каждого шага.
**How to apply:** Выбрать самое ценное + низкорискованное из известных задач, сделать, запушить. Не останавливаться на уточнения по мелочам.

**Особенно:** запрещены мягкие формы "спроса разрешения" — "если захотите — запустите X", "можете удалить сами", "хотите ли Y?", "если нужно — скажите". Всё это завуалированное "разрешишь?". Когда из запроса пользователя очевиден следующий шаг (например: "всё в одном репо" → отдельный репо больше не нужен → удалить), — просто делаешь и говоришь что сделал. Пользователь флагнул это дважды — значит сигнал sticky.

## Рефакторинг экранов

**Правило:** При рефакторинге экрана — двигаться по паттерну:
1. Читать весь файл полностью перед началом
2. Определить логические блоки JSX → отдельные компоненты
3. Компоненты с локальным state/useMemo забирают своё состояние внутрь
4. Компоненты с доступом к стору читают стор напрямую (не пробрасывать через пропсы)
5. Оркестратор держит только: shared computed state, handlers, composition
6. Создавать в `{screen-folder}/components/` с `index.ts` re-export
7. Коммитить и пушить сразу

**Why:** Паттерн выверен на ProgressScreen (1993→105), HomeScreen (970→232), ActiveWorkoutScreen (909→234), и на всех остальных больших экранах — все уже отрефакторены.

## Prisma

**Правило:** Использовать `npx prisma db push`. **Никогда** не запускать `prisma migrate dev`, `prisma migrate deploy`, `prisma migrate reset`.
**Why:** Проект не использует migration-файлы. Есть только live-схема и `db push`. `migrate dev` создаст новую историю и сломает deploy.
**How to apply:** После изменения `schema.prisma` → `npx prisma generate && npx prisma db push && npx tsc --noEmit`.

## Singleton Prisma + logger + Zod

**Правило:** 
- Prisma клиент импортировать только из `server/src/db.ts`, не `new PrismaClient()` в роутах
- Логи — только через `logger` из `server/src/utils/logger.ts`, не `console.*`
- На каждом серверном маршруте — Zod валидация входа

**Why:** Утечка 8 инстансов PrismaClient когда-то уже случилась. Structured logger нужен для LOG_LEVEL в проде.
