## CRITICAL

### C1. Production Android signing key + plaintext passwords committed to git
- **Where:** `credentials.json` and `android-keystore.jks` (repo root) — tracked in git, committed in `ab702d66` (2026-04-09). `git ls-files` confirms both are tracked **now**.
- **Evidence:** `android-keystore.jks` magic bytes `FE ED FE ED` (real Java KeyStore for `com.giron.app`). `credentials.json` holds `keystorePassword: "irongym2026"`, `keyPassword: "irongym2026"`, `keyAlias: "iron-gym"` in plaintext.
- **Why it's critical:** anyone with repo or git-history access has the app-signing key + passwords and can sign a malicious APK that Android accepts as a legitimate Giron update (app-impersonation / supply-chain). `.gitignore` lists both (lines 49-50) but that has **no effect** — they were committed before the rule, and `.gitignore` never untracks already-tracked files. A signing key is a rotate-on-exposure asset regardless of repo visibility.
- **Fix direction (needs founder action):** treat the key as compromised. (1) `git rm --cached` both files + commit + add to `.gitignore` [safe, reversible — agent can do]. (2) purge from history (git-filter-repo / BFG) + force-push [destructive — founder decision]. (3) generate a NEW upload/signing keystore in EAS managed credentials, rotate passwords (stop reusing `irongym2026`) [founder-only].

### C2. `app.listen()` runs unconditionally at module import
- **Where:** `server/src/index.ts:639`.
- **Why:** `const server = app.listen(PORT, …)` has no `NODE_ENV !== 'test'` guard (unlike the keep-warm ping at line 530). Every test that imports the app (supertest in `otp.test.ts`, `securityHeaders.test.ts`, `corsPolicy.test.ts`, `subscription_gating.test.ts`, …) binds a real TCP port; `startNewsRefreshScheduler()` and the admin-bootstrap `updateMany` also fire at import. Result: leaked TCP handles ("worker failed to exit gracefully"), `EADDRINUSE` risk on parallel suites, real side-effects during tests. (Real-world severity is bounded because tests currently pass via `--forceExit`, but it's the root cause of the handle leak and a correctness landmine.)
- **Fix:** gate `app.listen` + its callback side-effects behind `if (process.env.NODE_ENV !== 'test' && require.main === module)`; keep `export default app` for supertest.

## HIGH

### H1. `/user/change-password` and `/user/linked-accounts` missing the step-up rate limiter → password brute-force / account takeover
- **Where:** mount in `server/src/index.ts:361-365`; routes in `server/src/routes/user.ts` (`:525` linked-accounts). The strict `totpRateLimiter` (5/5min) covers `/2fa`, `/account`, `/change-email`, `/change-phone` — but **not** `/change-password` or `/linked-accounts`. Both accept `currentPassword` as step-up and have no per-account lockout (unlike `/auth/login`).
- **Why:** an attacker holding a stolen 60-min access token can brute-force the password at ~200 guesses/min via `/user/change-password`; a hit = full takeover (set new password → revoke sessions). The regression test `totpRateLimit.test.ts` doesn't assert these two endpoints, so the gap is untested.
- **Fix:** add `app.use('/api/user/change-password', totpRateLimiter)` and `app.use('/api/user/linked-accounts', totpRateLimiter)` before the generic `/api/user` mount; extend the test assertions.

### H2. axios 401 handler treats auth-endpoint 401s as "token expired" → forced logout + wrong login error
- **Where:** `src/services/api.ts:158` (no guard excluding `/auth/*`).
- **Why:** a wrong-password `POST /auth/login` returns 401 → interceptor enters the refresh block → no refresh token (user is logged out) → throws `'No refresh token'` → runs `clearTokens()` + `logout()` + a misleading "Сессия истекла" modal. The promise rejects with the synthetic Error (no `.response`), so `LoginScreen.tsx:121` can never match `INVALID_CREDENTIALS`/`WRONG_PASSWORD` — the user never sees "Неверный email или пароль".
- **Fix:** skip the 401-refresh block when `originalRequest.url` targets `/auth/login`, `/auth/refresh`, `/auth/totp-verify`, `/auth/login-by-phone`.

### H3. Queued requests during a token refresh are never marked `_retry` → second 401 re-drives refresh → spurious logout
- **Where:** `src/services/api.ts:160-165`.
- **Why:** requests parked in `failedQueue` are replayed via `api(originalRequest)` but `_retry` is never set on that branch (only the refresh-driving request sets it at line 168). If a replayed request 401s again (clock skew, route-specific auth failure), it re-enters the refresh path and can land in the force-logout catch.
- **Fix:** set `originalRequest._retry = true` before re-issuing the queued request in the `.then` at line 163.

### H4. `history.reverse()` mutates the shared array → AI context built from oldest messages
- **Where:** `server/src/routes/ai.ts:8318`.
- **Why:** `history.reverse()` reverses in place. `history` arrived newest-first (`orderBy createdAt desc`); after this line, later consumers that expect newest-first — `ai.ts:9345`, `:9472`, `:9038`, `:9276` (conversation-flow, emotional-response, recent-context builders) — silently read the **oldest** messages instead of the most recent, degrading AI context quality.
- **Fix:** build `rawMessages` from a copy: `[...history].reverse()`.

### H5. `latestVo2Max` uses `Array.sort()` with no comparator → wrong value shown (two locations)
- **Where:** `server/src/routes/health.ts:267-271` **and** the duplicate in `server/src/routes/ai.ts:5753` (`get_health_summary` AI tool).
- **Why:** default `.sort()` is lexicographic, so `[42, 9, 55].sort()` → `["42","55","9"]` and `.pop()` returns `9` instead of `55`. HealthScreen and the AI readiness logic show a wrong (usually understated) VO2 max. Intent is also muddled (sort+pop vs latest-by-date).
- **Fix:** decide semantic. "Max" → `Math.max(...)` / numeric comparator. "Latest" → sort rows by date desc, take first non-null. Fix **both** sites.

### H6. Nullable `externalId` in `@@unique` defeats health-sync dedup → duplicate rows on retry
- **Where:** `server/prisma/schema.prisma:635` (CardioSession), `:762` (SleepEntry), `:817` (HealthSample).
- **Why:** Postgres treats `NULL` as distinct under UNIQUE, so unlimited rows with `externalId = NULL` coexist. `health.ts:141-160` writes manual rows as `externalId: null` + `createMany({ skipDuplicates: true })` expecting dedup — so manual/null-externalId cardio & sample rows are never deduplicated; a retried sync (offline replay, double-tap) silently inserts duplicates.
- **Fix:** make the uniques partial (`WHERE externalId IS NOT NULL`, via raw SQL) and dedup null rows by a content key; or require `externalId` for watch-sourced rows.

### H7. Logout doesn't flush the throttled workout write → prior user's history leaks to disk
- **Where:** `src/store/useWorkoutStore.ts:908-910` + `src/store/useAuthStore.ts:300-308`.
- **Why:** the workout store persists via a 2s-throttled storage (buffers in memory, flushes after idle/background). `logout()` → `clearUserData()` is an in-memory `set()`, so the cleared blob sits in the throttle buffer. If the app is killed within 2s (or no flush fires while foregrounded), the previous account's encrypted workout history/PRs stay on disk and rehydrate on next launch — cross-account PII-at-rest leak the moment a 2nd account logs in on one device.
- **Fix:** `await flushPending()` on the throttled storage in `clearUserData()`/`logout()` (the wrapper already exposes it), or write the empty snapshot synchronously, bypassing the throttle.

### H8. Weekly-summary cron is N+1 with no concurrency bound and no sent-gate
- **Where:** `server/src/services/retentionService.ts:333,:356`.
- **Why:** selects up to 500 users (`take: 500`), then per user runs `Promise.all([workout.findMany{deep include}, workout.count])` + an SMTP send in a serial loop (~1000 DB round-trips + 500 serial emails per Sunday tick). No `weeklySummarySentAt` gate → a 2nd cron fire in the 18:00 UTC hour (deploy/restart) re-sends to everyone. At the 10k-MAU target this tick stalls for minutes.
- **Fix:** aggregate per-user volume with one `groupBy`/raw query; add a write-once sent gate (the code comment already concedes it's missing).

## Verified CLEAN (no action — recorded so they aren't re-audited)
- **Admin authorization:** all 55 `admin.ts` routes gated by `requireAdmin`/`requireStaff`; destructive/financial ops add step-up re-auth + last-admin guards.
- **Mass-assignment:** `PATCH /user/profile` uses a strict Zod allowlist — `role`/`isBanned`/`isAdmin` not settable from body.
- **OAuth:** Google `email_verified` + audience + freshness + jti replay; VK/Yandex validated server-side; email auto-link blocked unless existing account verified that email.
- **Tokens:** access/refresh split secrets, HS256 pinned, SHA-256 refresh hashing, rotation + reuse detection, invalidated on logout/password/email/phone change.
- **Password reset:** 32-byte CSPRNG, SHA-256 stored, 1h expiry, atomic single-use, generic response, sessions wiped.
- **AI tool args:** all ~42 + 6 context tools `safeParse` model output before any DB write; userId scoping never trusts message content; prompt fields sanitized (`sanitizeForPrompt`).
- **Transactions:** workout-complete, meal edits, program activation, routine replace all wrapped in `$transaction`; concurrent program-activation race closed in-tx.
- **Client UI runtime:** no new crash-on-undefined, uncleared-timer, stale-closure, or unhandled-async defects in the audited surface (timers/listeners/Animated loops all cleaned on unmount).
- **Nav guard:** cannot reach Main unauthenticated; renders gate until hydration; deep links scheme-allowlisted.
- **OTA:** failed check/download can't brick the app (all wrapped, activation deferred to cold start).
- **TS strictness / CI gate / test integrity:** `strict:true` both sides, zero `@ts-nocheck`/`.only`/`.skip`; CI runs tsc+tests+build with no `continue-on-error`; no committed `.env`, no hardcoded prod secrets in source.
