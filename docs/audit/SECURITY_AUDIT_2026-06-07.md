# Security Audit — Giron (2026-06-07)

> Многоагентный аудит: разведка attack-surface → 18 направлений → состязательная
> проверка каждой находки (отсев ложных) → синтез. **45 сырых находок → 19 подтверждённых**
> после adversarial-проверки. Отчёт собран вручную (агент-синтезатор упёрся в лимит сессии).
> Контекст: 1 реальный пользователь (founder/admin), реальных юзеров нет, рынок РФ/RuStore.

## 🔴 CRITICAL

### C1. Ключ подписи Android + пароли лежат в git-истории (никогда не вычищались)
**Файлы:** `android-keystore.jks`, `credentials.json` — коммит `ab702d66`
Кто угодно с доступом к репо (он **публичный** — github.com/seva1223423/giron) или к любому форку/старому клону делает `git show ab702d66:credentials.json` и получает:
`keystorePassword="irongym2026"`, `keyAlias="iron-gym"`, `keyPassword="irongym2026"` + сам `.jks` (проверено: магия `FE ED FE ED` — настоящий keystore).

**Чем грозит:** обладатель ключа собирает вредоносный APK, который Android примет как **легитимное обновление Giron** (та же подпись = та же личность приложения). Ключ подписи **нельзя отозвать**. Коммит `3ddd4a4c` сделал только `git rm --cached` (убрал из отслеживания), но историю не переписал — объекты на месте и запушены.

**Варианты:**
| # | Вариант | Плюсы | Минусы / усилия |
|---|---|---|---|
| A *(рекоменд.)* | Считать ключ скомпрометированным: новый keystore + новые пароли; для Play — Play App Signing rotation; для RuStore/прямого APK ротации нет → перевыпуск. Затем `git filter-repo`/BFG вычистить `.jks`+`credentials.json` из ВСЕЙ истории, force-push, все клоны заново. Подпись хранить только в EAS managed credentials. | Закрывает необратимо | **Founder-only**, L (час-два + переустановка у тех у кого стоит) |
| B | Сделать репозиторий **приватным** + ротация ключа без переписывания истории | Быстро (5 мин на приватность) | История с ключом остаётся в форках/клонах; ключ всё равно надо ротировать |
| C | Только ротация ключа, историю не трогать | Минимум работы | Старый ключ продолжает быть в публичной истории — полумера |

> ⚠️ Реальных пользователей нет → немедленная эксплуатация маловероятна, но компрометация **необратима**, поэтому ротация ключа обязательна перед любым реальным релизом. Это тот самый C1 из прошлого аудита — так и не закрыт.

## 🟠 MEDIUM

### M1. Access-токены переживают logout / смену пароля / reset / отключение 2FA
**Файл:** `server/src/middleware/auth.ts` (`authenticate` L13-104); точки отзыва: `auth.ts` /logout L1521-1548, /reset-password L1648-1652; `user.ts` /change-password L570-574, DELETE /sessions L725-733
Access-токен — stateless JWT на 60 мин. `authenticate` проверяет подпись и грузит только `{isBanned, role, lockedUntil}` — **никогда** не сверяется с отметкой инвалидации. Все «выйти на всех устройствах», смена пароля, reset, отключение 2FA отзывают **только refresh-токены**. Уже выданный access-токен живёт до своего `exp` (до 60 мин).

**Чем грозит:** юзер сменил пароль после утечки / нажал «выйти везде» — а атакующий с уже украденным access-токеном сохраняет полный доступ ещё до часа. Защита, которую юзер «сделал», молча не работает.

**Варианты:**
- **A (рекоменд.):** добавить `User.tokensValidAfter` (DateTime) или `tokenVersion` (int). На любом revoke-all ставить `tokensValidAfter = now()` + сбросить `authUserCache`. В `authenticate` после verify отвергать токен с `iat < tokensValidAfter`. Включить поле в существующий 60-сек кэш → 0 лишних запросов. Усилие **S-M**. Окно падает с 60 мин до ≤60 сек.
- **B:** сократить TTL access-токена (напр. 15 мин). Проще, но окно всё равно ненулевое и чаще дёргается refresh.
- **C:** хранить access-токены в БД (stateful). Надёжно, но дорого по запросам — против самой идеи stateless JWT.

### M2. Нет per-account блокировки brute-force 2FA на step-up эндпоинтах
**Файл:** `server/src/routes/user.ts` — change-password L548, change-email L1046, change-phone L1207, linked-accounts, /2fa/disable, /2fa/backup-codes; хелперы в `auth.ts` L59-76
Per-account счётчик неудач 2FA (`is2faLocked`/`record2faFailure`) был добавлен именно потому, что IP-лимитер (5/5мин) обходится сменой IP. Но применён он **только** в `/auth/totp-verify`. Все остальные step-up точки полагаются лишь на IP-лимитер.

**Чем грозит:** атакующий с украденным access-токеном перебирает 6-значный TOTP, меняя IP, без потолка на аккаунт — рано или поздно попадает в одно из 3 валидных значений и делает чувствительное действие.

**Варианты:**
- **A (рекоменд.):** переиспользовать `is2faLocked`/`record2faFailure`/`clear2faFailures` на КАЖДОМ эндпоинте со step-up (экспортировать их из `auth.ts`). Усилие **M**, закрывает корень.
- **B:** навесить строгий `totpRateLimiter`, но **с ключом по userId, а не IP**. Усилие S, но слабее (не покрывает пароль-перебор).

### M3. Admin step-up TOTP не покрыт строгим лимитером
**Файл:** `server/src/routes/admin.ts` `requireAdminStepUp()` L56-93; лимитер `index.ts` L410 (200/15мин/IP)
Самые опасные операции (смена роли, бан, удаление юзера, force-logout, force-disable-2fa) защищены `requireAdminStepUp()`. Но на `/api/admin` висит только общий лимитер 200/15мин/IP — ни строгого `totpRateLimiter` (5/5мин), ни per-account локаута. То есть второй фактор на **самых разрушительных** действиях защищён слабее, чем обычный 2FA юзера.

**Чем грозит:** атакующий с admin-токеном + знанием admin-пароля перебирает TOTP ~200/15мин/IP × смена IP, без локаута аккаунта.

**Варианты:**
- **A (рекоменд.):** внутри `requireAdminStepUp` вызвать `record2faFailure`/`is2faLocked` по `req.userId` (те же хелперы, что в M2) + добавить `isTotpReplay`. Усилие **S** (после M2 — почти бесплатно).
- **B:** примонтировать `totpRateLimiter` на `/api/admin` со step-up. Проще, но per-IP — обходится сменой IP.

### M4. VK access-token не проверяется по audience (возможен confused-deputy)
**Файл:** `server/src/routes/auth.ts` POST /auth/vk L917-1028; то же в `user.ts` linked-accounts L1349-1371
Google пинит `audience: GOOGLE_CLIENT_IDS`, Яндекс **требует** `client_id === YANDEX_CLIENT_ID`. А VK — **нет**: только проверка наличия `VK_APP_ID` + вызов публичного `users.get`. Какому VK-приложению выдан токен — не проверяется.

**Чем грозит (условно):** если VK `users.get` принимает токен, выданный *другому* VK-приложению, то токен жертвы, украденный из чужого VK-приложения, даёт полный вход в Giron-аккаунт. *(Проверяющий снизил high→medium: само поведение VK-платформы из кода не доказуемо — современные VK ID токены обычно привязаны к приложению. Но дыра в консистентности реальна.)*

**Варианты:**
- **A (рекоменд.):** перейти на server-side обмен **кода** (не implicit-токена) через `id.vk.com/oauth2/auth` с серверным client_secret и проверкой `client_id == VK_APP_ID`. Усилие **M**. *(VK-вход сейчас всё равно не активен — ключей нет, кнопка скрыта → можно сделать сразу правильно перед включением.)*
- **B:** вызвать `secure.checkToken` (нужен service-token) и сверить app_id. Усилие S-M.
- **C:** не включать VK-вход, пока не сделан A. Бесплатно (статус-кво).

## ⚪ INFO (2)

- **I1.** Per-user минутный бакет AI применён только в `/chat`; остальные AI-роуты — только per-IP. Это структурная причина L3/L4/L5. Фикс — стандартизировать per-user квоты (см. L12).

## ✅ Что проверено и ОК (покрытие)

- **SQL-инъекции:** нет `$queryRaw`/`$executeRaw` с интерполяцией — Prisma параметризует всё.
- **IDOR / доступ к чужим данным:** все мутирующие маршруты и AI-tools привязаны к `req.userId` (проверены delete_meal/modify_meal/delete_cardio/activate_program/modify_workout/add_recipe_to_diary и др.). Кросс-тенант доступа не найдено.
- **Google/Yandex OAuth:** audience/client_id проверяются, replay-кэш (jti), `email_verified` guard, freshness-окно `iat` — сделано правильно.
- **Command injection в ffmpeg:** аргументы не строятся из пользовательского ввода опасно; ffmpeg с hard-timeout 30с; ext берётся через whitelist-regex.
- **Валидация входа:** Zod покрывает тела/параметры; mass-assignment не найден.
- **PII в логах:** logger/Telegram/Sentry скрабят `totpSecret`, токены и пр. (пины в тестах).
- **CORS/helmet:** allowlist не рефлективный; `trust proxy` выставлен корректно (лимитеры бьют по реальному IP).
- **Крипто:** пароли — bcrypt; refresh/reset/trusted-device — SHA-256; freshness и replay у OAuth.
- **Ответы API:** `totpSecret`/хэши/токены вырезаются из ответов.

## Приоритетный план (с учётом: 1 админ, реальных юзеров нет, РФ/RuStore)

1. **Перед любым реальным релизом — C1** (ротация ключа подписи + чистка истории). Founder-only, необратимо. До этого можно жить (юзеров нет).
2. **Быстрые XS-победы сейчас** (10-15 мин суммарно): L7 (проверка JWT-секретов), L10 (cardio-санитайзер), L11 (убрать memory из репо). Низкий риск, чистый выигрыш.
3. **2FA-связка M2+M3+L1** — один заход: экспортировать хелперы локаута и навесить на все step-up + admin + починить отключение 2FA. Усилие M, закрывает 3 находки разом.
4. **M1 (kill-switch access-токенов)** — одно поле `tokensValidAfter` + проверка в `authenticate`. Делает logout/reset реально работающими.
5. **Контроль расходов на AI** (L3/L4/L5/L6 + L12) — один заход: единая per-user дневная квота для всех платных LLM/STT-роутов. Важно перед запуском (деньги).
6. **M4 (VK)** — сделать правильно ПЕРЕД включением VK-входа (сейчас отключён).
7. **L8/L9** (шифрование TOTP-секрета, усиление backup-кодов) — defense-in-depth, можно позже.
